# デモの自己申込み（承認制の廃止）— 展開手順

承認制をやめ、**メールの確認番号だけでその場でデモが始まる**ようにした。
そのかわり「同じ会社が名前を変えて何度でもデモを取る」をサーバー側で止める。

アプリ側の変更だけでは動かない。**Supabase 側の2つを先に入れること**。

---

## 1. SQL を流す（Supabase ダッシュボード → SQL Editor）

`learning-server/rls-step5-self-serve-demo.sql` をそのまま貼って実行する。

やっていること:
- `remote_licenses` に列を足す（device_hash / contact_email / email_key / email_domain /
  company_key / expires_at / verify_code ほか）
- 同一性の鍵に**部分UNIQUE索引**を張る（NULL は衝突しないので、既存の有料ライセンスは無傷）
- `consume_credits_seat` に**期限の判定**を足す（期限切れは単位が残っていても消費させない）

## 2. Edge Function `license` を差し替える

ダッシュボード → Edge Functions → `license` → Code タブに
`supabase/functions/license/index.ts` の中身を貼って Deploy。

増えたアクション:
- `demo_start`  … 申込み。確認番号をメールで送る（トークンはまだ返さない）
- `demo_verify` … 番号の照合。合えば有効化してトークンを返す

`send-mail` 関数のシークレット（SMTP_USER / SMTP_PASS / OWNER_EMAIL）が
設定済みであること。確認番号のメールはそこを経由して送る。

## 3. アプリを配る

v3.8.3 以降。ログイン画面の「無料デモを今すぐ始める」から2段階で開始できる。

---

## 誰が弾かれるのか（1社1デモの担保）

申込みが来たら、次の順で既存を探す。**1つでも当たれば新しいデモは配らない**。

| 鍵 | 効くケース |
|---|---|
| `device_hash`（端末の指紋） | アプリを入れ直す・DBを消す・会社名を変える |
| `email_key`（正規化メール） | `n.a.ka.no+demo2@gmail.com` のような別名 |
| `company_key`（正規化会社名） | 「株式会社◯◯」「(株)◯◯」「◯◯ 」の書き分け |
| `company_name` そのまま | 承認制のころに作られた既存行との突き合わせ |

当たったときは**登録済みのメール宛**に確認番号を送る。
→ 会社名を変えただけの他人は番号を受け取れないので通れない。
→ 本人なら、**残っている単位と期限のまま**再開できる（増えない・延びない）。

会社ドメイン（フリーメール以外）が同じ2件目は、その場でお断りして
「参加コードで参加」へ案内する。運営には通知メールが飛ぶ（＝増員の商談の芽）。

**残る穴**: 新品のPC＋新規のフリーメール＋実在しない会社名なら、もう一度10単位を取れる。
これを塞ぐには電話番号のSMS確認まで要るので、いまは割に合わないと判断した。
（＝1回あたり「新しいPC1台と実在するメール1つ」が必要。10単位のために払う手間としては重い）

## 期限の扱い

- デモの期限は `remote_licenses.expires_at`（サーバー）が正。**14日**（2026-09-03に30日から変更）。
- アプリはそれを `tenants.plan_expires_at` に写して残り日数を出す。
  以前は開始日をローカルDBだけで持っていたので、**入れ直すと期間が復活していた**。
- 期限切れは `verify` が `active:false` を返し、`consume` も RPC で弾く。
- **有料に上げるときは `expires_at` を NULL に戻すこと**（admin approve は自動でやる）。
  残っていると、お金をいただいたのに14日で止まる。

## 承認制の名残

- `register_pending` と管理画面の「承認/却下」はそのまま残してある
  （承認制のころに作られた pending 行のため）。
- 新規のデモはここを通らない。管理画面で承認するのは**有料への引き上げ**だけになる。
